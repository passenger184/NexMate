# Design: durable-tool-execution-audit

## Context

See `proposal.md` (Why). Current state after M4: Frappe authenticates chat, owns conversation state, derives per-request retrieval scope, and validates the `chat-only` envelope, but tool execution remains process-local: proposals live in RAM (`tools/edit.py`, `tools/erpnext_write.py`) with TTL/expiry checked only in inference, no durable actor/site binding, no immutable approved payload guarantee, no recheck at execution, no serialization of concurrent conflicting operations, no idempotency/uncertain-outcome reconciliation, and audit is partial (`data/erpnext_writes.jsonl`, Git history, request telemetry) with no correlated ledger or recovery. G3 retired the JSON session store; M4 added site/ACL and generation-scoped indexes plus a deny-by-default egress boundary. The HLD approved target is Frappe-owned durable proposals/approvals with separate private inference and a confined code executor, plus a correlated audit covering every leg; physical tenancy, ingestion ownership, and version/packaging remain future gates.

## Goals / Non-Goals

**Goals:** Durable Frappe-owned proposal/approval lifecycle with immutable exact payload/diff, ownership/expiry/revocation semantics, permission recheck at execution, serialized conflicting operations, idempotent retry and uncertain-outcome reconciliation; separate confined code executor under Frappe authorization; correlated lifecycle audit with redaction/access/retention/recovery; policy-filtered Debug disclosure without leaking denied sources.

**Non-Goals:** Selecting physical per-site vs shared tenancy (U1), mediated-vs-direct store placement beyond the durable-record contract (U2), full ERPNext permission parity beyond the coarse-grained tiers (U5), production egress grants or private-data cloud consent (U6), app versioning/Frappe compatibility matrix and monorepo-to-Bench packaging (U8), operational latency/quality/recovery budgets (U9), MCP or Developer Workbench (deferred).

## Decisions

- **D0 — Durable Frappe record is the proposal truth (proposed).** `NexMate Tool Proposal` is a Frappe DocType (separate from Conversation) with immutable fields `operation`, `target`, `payload|diff`, `reason`, `actor`, `site`, `correlation`, `expiry`, `preconditions`, plus lifecycle `status` (`pending`→`approved`/`rejected`→`executing`→`succeeded`/`failed`/`denied`/`uncertain`→`reconciled`). State transitions are Frappe-owned, row-locked, and audited. Alternative (keep RAM proposals with inference-owned state) rejected: loses durability, ownership, and restart safety.
- **D1 — Immutability means new proposal on any change (proposed).** The approved record stores a hash of the exact payload/diff + target; execution verifies byte-for-byte equality. Any edit to payload/target/reason creates a new proposal requiring new approval. Already-delivered answers remain historical. Alternative (allow amendment of approved payload in place) rejected: breaks human-approved exact-payload guarantee.
- **D2 — Recheck at execution, not only at proposal (proposed).** Immediately before execution Frappe re-derives identity/site, revalidates permission, target existence/state, and approval/expiry/revocation, inside the same Frappe transaction scope as the state transition to `executing`. On failure the proposal transitions to `denied` with a correlated audit entry, not to `executing`. Alternative (recheck only at proposal) rejected: permissions and target state can change between approval and execution.
- **D3 — Concurrency and idempotency via precondition + advisory lock (proposed).** Each proposal carries a concurrency precondition (e.g., `expected_version` or `target_hash`). Frappe acquires an advisory/row lock on the target key, checks the precondition, then executes; conflicting concurrent proposals are serialized and the later is rejected as `conflicting` with a correlated audit, or made idempotent when the same payload repeats with the same idempotency key. No blind overwrite. Alternative (optimistic write without precondition) rejected: permits silent overwrites.
- **D4 — Uncertain-outcome reconciliation without blind replay (proposed).** Executor transports return typed outcomes including `uncertain` (timeout with unknown upstream result). Frappe transitions the proposal to `uncertain`, performs an explicit read-back/reconciliation of the target, then transitions to `succeeded` or `failed` with a reconciled audit entry. Retries use the same idempotency key and never re-apply a write whose outcome is still `uncertain` without prior reconciliation. Alternative (auto-retry on timeout) rejected: risks duplicate writes.
- **D5 — Separate confined executor, inference never writes (proposed).** Code edits execute only in the confined executor boundary, invoked by Frappe after approval and recheck. The executor enforces root-containment, tracked-not-ignored, clean-tree, and per-edit atomic commit for exactly the approved diff, returning the commit hash or a typed failure. Inference may request a tool but cannot execute it, choose a repository, or approve its own output. Alternative (let inference apply edits directly) rejected: violates least-privilege and authorization contracts.
- **D6 — Correlated ledger is Frappe-owned, not inference-local (proposed).** Audit writes are Frappe-owned durable records (not inference-local JSONL) keyed by `correlation`/`request`/`action` plus actor/site, covering `proposal_created`, `approved`/`rejected`/`expired`, `recheck`, `execution_attempt`, `succeeded`/`denied`/`failed`/`uncertain`/`reconciled`, plus permitted retrieval provenance and security events. Inference emits intent; Frappe persists the authoritative ledger entry and enforces redaction/access/retention/tamper checks. Alternative (keep post-write JSONL in inference) rejected: not durable, not actor-bound, not recoverable.
- **D7 — Debug is policy-filtered, minimized, and audited (proposed).** Debug disclosure is a separate Frappe read path that returns only permitted provenance, actually accessed documents/fields, and raw results/queries where they exist, filtered by the same scope that authorized retrieval/execution and by an explicit `debug_view` permission. Every Debug view is itself audited. No SQL-generation feature is introduced. Alternative (dump raw prompts/results) rejected: leaks denied sources and sensitive fields.

## Risks / Trade-offs

- [Risk] Durable proposals add write latency and storage → Mitigation: DocType uses indexed actor/site/status/correlation, short expiry (bounded, e.g., 15 min mirroring current TTL) limits table growth; old proposals archived per retention policy, never deleted silently.
- [Risk] Strict immutability increases proposal churn on iterative edits → Mitigation: UI can offer “revise” that clones with new reason/payload and links correlation, but still requires new approval; not a silent amendment.
- [Risk] Advisory locking on hot targets serializes throughput → Mitigation: lock is per-target key, not global; conflicts are audited and retry guidance returned, not silently queued indefinitely.
- [Risk] Separate executor adds operational complexity → Mitigation: executor validates only the approved immutable diff, returns typed errors/timeouts, and remains confinement-scoped; placement (same host vs separate worker) is deployment wiring, not a second application.
- [Risk] Audit durability doubles writes → Mitigation: Frappe transaction includes proposal state and audit entry; on audit-persist failure the execution outcome is recorded as `audit_pending` and reconciled by a repair job before claiming a complete transaction.

## Migration Plan

1. Land `NexMate Tool Proposal` DocType and audit ledger DocType behind a permissive-but-logging flag: new proposals write durably while legacy RAM paths remain behind the same flag, both validated but only durable path executes when flag is on.
2. Migrate in-flight RAM proposals to durably rejected/expired on first restart after cutover (no silent carryover); legacy JSONL remains readable for history, not authoritative.
3. Add executor integration and Frappe approval API, register explicit tool contracts (read/retrieval/code-search vs code-edit/business-write), seed the `debug_view` permission, and publish the durable-only execution mode.
4. Flip enforcement on (durable-approved-only execution, no direct inference apply); run contract/approval/concurrency/uncertain-outcome/audit/Debug suites and the G4 negative suites.
5. Rollback at any step: disable durable execution, re-enable chat-only gateway behavior; durable records remain for audit but cease gating execution.

## Open Questions

None that change specs, approach, or tasks. Exact DocType field names, correlation ID format, lock timeout, and redaction field lists are set during implementation within the bounds above.
